Paste this into your coding agent

This is the fastest path. Your agent can inspect the project and guide the setup, while you keep every token and secret out of the conversation.

Agent setup prompt
Help me set up least-privileged 1Password access for this project.

Security rules:
- Never ask me to paste a token or secret into chat.
- Never print, log, summarize, or commit secret values.
- Use a dedicated vault and a narrowly scoped service account.
- Default to read-only access. Add write access only if this project truly needs it.
- Resolve secrets only when the consuming command runs.

Workflow:
1. Inspect this project and propose a namespace using
   <project>/<service>/<environment>.
2. Check that 1Password CLI 2.18.0+ and jq are installed.
3. Guide me through creating a dedicated vault on 1Password.com.
   Pause while I complete web-only steps.
4. Guide me through creating a service account with access only to that vault.
   Explain that its vault access and permissions cannot be changed later.
5. Tell me to save the one-time token in my personal 1Password vault.
6. Have me load it without shell history:
   read -rsp "1Password service-account token: " OP_SERVICE_ACCOUNT_TOKEN
   export OP_SERVICE_ACCOUNT_TOKEN
   printf '\\n'
7. Verify the session with `op user get --me` without revealing the token.
8. Store items as API Credential records with semantic fields such as
   credential, username, host, and port. Tag explicitly agent-safe.
9. Add a short secrets policy to this project's AGENTS.md or equivalent.
10. Show the exact `op run`, `op inject`, or `op read` command this project
    should use. Do not create plaintext secret files.

Do not make destructive changes. At the end, summarize vault name,
item references, permissions, and checks performed—but never secret values.

The quick rundown

Create one vault as a trust boundary. Give one service account only the permissions it needs in that vault. Load its one-time token into the shell that launches your coding agent. Store secrets as predictable item references, and tell the agent to resolve those references only when a command needs them.

Stop 1

Create a dedicated vault online

A vault should describe a trust boundary, not become another miscellaneous drawer.

  1. Sign in at 1Password.com.
  2. On the Home page, choose New Vault.
  3. Name it for the access boundary, such as Agent Automation, add a plain description, and select Create Vault.
  4. Put only credentials an automated coding session genuinely needs in this vault.
Do not use a built-in personal vault. 1Password service accounts cannot access built-in Personal, Private, Employee, or default Shared vaults. A purpose-built vault also makes least privilege visible and auditable.
Stop 2

Create the service account and copy its token

This is the “vault key” used by headless tools. 1Password calls it a service account token.

  1. Open the service account wizard. The manual path is Developer → Directory → Other → Create a Service Account.
  2. Choose a narrow name, such as local-coding-agent.
  3. Select only the dedicated vault. Grant read items; add write items only if the agent must create or rotate secrets.
  4. Leave “can create vaults” off unless vault creation is part of the automation.
  5. Create the account, then immediately choose Save in 1Password. Store the token in a personal vault the service account cannot access.
The token appears once. Do not paste it into a prompt, source file, issue, shell profile, or chat. Service-account vault access and permissions are immutable; create a replacement account if the scope must change.

Read-only account

Default for builds, tests, deployment reads, and existing API credentials.

Read-write account

Separate token for explicit provisioning or rotation work. Launch it only for that task.

Stop 3

Load the token into one shell

The required variable name is OP_SERVICE_ACCOUNT_TOKEN. Use a hidden prompt so the value does not enter shell history.

bash / zsh — current session
read -rsp "1Password service-account token: " OP_SERVICE_ACCOUNT_TOKEN
export OP_SERVICE_ACCOUNT_TOKEN
printf '\n'
op user get --me

If op user get --me reports a service account, authentication works. 1Password CLI 2.18.0 or later is required.

Launch the agent without writing the token to disk

For a repeatable local launcher, store the service-account token as an item in your personal 1Password vault, then create a non-secret reference file:

.env.agent — safe to version only if the path reveals nothing sensitive
OP_SERVICE_ACCOUNT_TOKEN=op://Private/local-coding-agent/credential
Choose the tool you use
op run --env-file=.env.agent -- codex
op run --env-file=.env.agent -- claude
op run --env-file=.env.agent -- omp

Your personal 1Password session resolves the reference for the child process. Inside that process, op authenticates as the restricted service account. Adjust the item path and executable names to your setup.

Environment variables are not a sandbox. The launched agent process can access its own token. The protection comes from the service account’s narrow vault scope, not from hiding the variable from that process.
Stop 4

Namespace every secret

Predictable names remove guesswork without revealing secret values.

Projectexample-app
Servicepayments-api
Environmentprod

Use the item title <project>/<service>/<environment>. Put values in semantic fields such as credential, username, host, or port.

Example reference — illustrative only
op://Agent Automation/example-app/payments-api/prod/credential

Add tags that answer operational questions: env:prod, api-key, rotates:quarterly, and an explicit allow-list tag such as agent-safe. A tag is metadata—not access control.

Stop 5

Give the agent a narrow contract

Put this in AGENTS.md, CLAUDE.md, or the equivalent project instruction file.

Reusable agent instructions
## Secrets

- Use the `op` CLI. Never ask the user to paste a secret into chat.
- Access only the vault already authorized for this session.
- Item titles use: `<project>/<service>/<environment>`.
- Resolve secret references only when the consuming command runs.
- Prefer `op run`, `op inject`, or a single `op read` over plaintext files.
- Never print, log, summarize, or commit secret values.
- Treat `agent-safe` as an allow-list convention, not access control.
- Store new credentials as API Credential items with semantic field names.
- Stop if a requested item is outside the authorized vault or scope.

The instruction file improves behavior; the service account enforces the actual boundary. Assume prompts can fail and permissions must still hold.

Tool

Bootstrap one namespaced credential

The web-only steps—creating the service account and saving its one-time token—remain manual. This script validates the restricted session, checks vault access, accepts a secret through hidden input, and creates a namespaced API Credential item without putting its value in argv or shell history.

Download bootstrap-agent-vault.sh Requires: bash, op, jq
Run it
chmod +x bootstrap-agent-vault.sh
./bootstrap-agent-vault.sh \
  "Agent Automation" \
  "example-app/payments-api/dev" \
  "dev"
What the script deliberately does not do
  • It does not generate or print a service-account token.
  • It does not broaden vault permissions.
  • It does not put a secret in a command argument.
  • It does not create a vault when the service account cannot see the requested one.
